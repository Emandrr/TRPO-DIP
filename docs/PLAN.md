# PLAN.md — Построение системы СА-ЭКГ (инструкция для LLM-агента)

> Документ предназначен для LLM-агента (Claude Code / Cursor / аналог), который реализует систему по шагам.
> Источник: ТЗ по ГОСТ 34 «Система для анализа и хранения кардиологических исследований (СА-ЭКГ)».
> Принцип: агент НЕ задаёт вопросов по пунктам, где ниже зафиксировано решение (раздел 3). Всё, что не определено, — записывается в `docs/ASSUMPTIONS.md` и реализуется по наиболее безопасному варианту.

---

## 0. Правила работы агента

1. Работай строго по фазам (раздел 7), по порядку. Не начинай фазу N+1, пока не выполнены критерии приёмки фазы N (команды проверки указаны в каждой фазе).
2. Одна задача = один коммит. Сообщение коммита: `<ID задачи>: <краткое описание>`.
3. Каждая задача сопровождается тестами. Задача без тестов не считается выполненной.
4. Не меняй контракты из раздела 5 (API) и раздела 4 (модель данных) без записи в `docs/DECISIONS.md` (дата, причина, затронутые файлы).
5. Не используй библиотеки с лицензиями, ограничивающими использование (GPL/AGPL/SSPL/коммерческие). Допустимы MIT, Apache-2.0, BSD, ISC, MPL-2.0. Веди `docs/LICENSES.md` (пакет, версия, лицензия).
6. Любое значение из ТЗ (пороги, диапазоны, форматы) выноси в константы/конфиг с комментарием-ссылкой на пункт ТЗ. Магических чисел в коде быть не должно.
7. Все сообщения пользователю — на русском. Код, идентификаторы, комментарии, коммиты — на английском (кроме ссылок на пункты ТЗ).
8. Не логируй пароли, токены, содержимое медицинских данных. В логи пиши идентификаторы и коды ошибок.
9. После каждой фазы обнови `docs/PROGRESS.md`: что сделано, что отклонено от плана, что осталось.

## 1. Контекст системы (кратко)

- **Назначение:** приём готовых CSV-файлов ЭКГ (250 Гц), валидация, фильтрация, автоматическое выявление нарушений ритма и отчёт; ведение медкарты, диагнозов, рекомендаций, назначений. Съём ЭКГ в систему НЕ входит.
- **Роли:** `Patient`, `Doctor`, `Admin`.
- **Архитектура:** Angular SPA ⇄ (HTTPS, JSON) ⇄ ASP.NET Core Web API ⇄ PostgreSQL (всё, кроме сигналов) + DuckDB (данные CSV/сигналы).
- **Режимы:** штатный и администрирования.
- **Вне объёма (НЕ реализовывать):** интеграция с внешними системами, новые виды обследований, дополнительные алгоритмы анализа, регистрация сигнала с датчика.

## 3. Принятые решения по неоднозначностям ТЗ (не обсуждать, реализовать)

| # | Вопрос | Решение |
|---|---|---|
| D1 | «Сессия мониторинга» в п. 4.3.2 ТЗ — ошибка формулировки | Сущность не создавать и не показывать на схемах. Единица учёта — `EcgRecord` (одна загрузка = одно исследование ЭКГ). |
| D2 | Согласие на обработку ПД подписывается в учреждении | В `Patient` поле `ConsentSigned` (bool, по умолчанию `false`) и `ConsentSignedAt`. Пока `false` — пациент может войти, но API загрузки ЭКГ возвращает 403 с кодом `CONSENT_REQUIRED`. Отметку ставит Admin. |
| D3 | Внешний доступ только для пациентов | Реализовать на уровне приложения: настройка `Security:ExternalAccessAllowedRoles = ["Patient"]` + IP-диапазоны внутренней сети в `Security:InternalNetworks`. Запрос не из внутренней сети от Doctor/Admin → 403 `INTERNAL_NETWORK_ONLY`. По умолчанию в dev-профиле проверка выключена флагом. |
| D4 | Пациент видит ЭКГ-отчёт только после «принятия» врачом | Пациенту отдаются только записи, у которых отчёт в статусе `Accepted`. Отклонённые и необработанные — скрыты. |
| D5 | Пол неизвестен → порог QTc неясен | Пол обязателен в медкарте (приложение В). Если анализ запущен для пациента без медкарты/пола — анализ завершается статусом `Failed`, код `PATIENT_SEX_REQUIRED`. Загрузка файла при этом допустима, анализ перезапускается после заполнения (`POST /ecg-records/{id}/reanalyze`). |
| D6 | Отведение не указано в CSV | Считать все данные отведением II (эталон амплитуды R из таблицы Д.1). Указать это в отчёте строкой «Принято отведение II». |
| D7 | Что удаляется через 1 месяц / 10 лет | Через 30 суток после загрузки удаляются **сырые** отсчёты (`raw`). Отфильтрованный сигнал (`filtered`) удаляется через 10 лет с момента создания. Записи `EcgRecord`, `AnalysisReport`, `Anomaly`, диагнозы остаются. После удаления `raw` статус записи `RawPurged = true`. |
| D8 | Удаление данных админом/врачом | Мягкое удаление (`IsDeleted`, `DeletedAt`, `DeletedBy`) для: медкарты, диагноза, рекомендации, назначения, устройства. Фильтр `IsDeleted = false` на уровне EF Core global query filter. Физическое удаление — только фоновой очисткой по D7. |
| D9 | Регистрация врачей/админов | Только Admin. Создаётся с временным паролем; флаг `MustChangePassword = true`. |
| D10 | Временный пароль | 12 символов (буквы разного регистра, цифры, спецсимволы), генерируется криптостойко, показывается и выдаётся в PDF **один раз**; в БД — только хеш. После первого входа обязательная смена пароля (все остальные эндпоинты кроме смены пароля отдают 403 `PASSWORD_CHANGE_REQUIRED`). |
| D11 | Политика паролей | Минимум 8 символов, минимум одна буква и одна цифра. |
| D12 | Токены | Access JWT — 15 минут; Refresh — 7 суток, хранится хешем в БД, ротация при каждом обновлении, отзыв при блокировке/смене пароля. |
| D13 | Блокировка при переборе | 5 неудачных входов подряд → блок на 15 минут (по аккаунту + по IP rate limit). |
| D14 | Максимальный размер загрузки | 1 ГБ (жёсткий лимит Kestrel и `RequestSizeLimit`), потоковое чтение без буферизации в память. |
| D15 | Обработка анализа | Асинхронная. Загрузка возвращает `202 Accepted` + `recordId`. Статусы: `Uploaded → Validating → Queued → Processing → Done | Failed`. Валидация синхронная (до сохранения), анализ — в фоне. |
| D16 | Валидный файл с частично непригодными данными | Сохраняется; непригодные интервалы (Error, разрывы) фиксируются в `ecg_gaps` и показываются в отчёте. |
| D17 | Слияние аномалий | Однотипные аномалии, разделённые менее чем 5 с, сливаются в один интервал; в отчёте хранится min/max значение показателя. |
| D18 | Формат времени | Хранить `timestamp` как UTC-наивное локальное время файла в `TIMESTAMP(3)`; в API отдавать ISO 8601 без смещения плюс поле `offsetMs` от начала записи. |
| D19 | Приложение Б (пример отчёта) недоступно в тексте | Структура отчёта определена в разделе 6.6. Верстку сверить с приложением Б вручную и поправить только представление, не структуру данных. |

### 4.2 DuckDB (отдельный файл `ecg.duckdb`, путь из конфига)

```
raw_samples(record_id UUID, offset_ms BIGINT, ts TIMESTAMP, value SMALLINT)       -- только пригодные отсчёты, после дедупликации
filtered_samples(record_id UUID, offset_ms BIGINT, value REAL)                     -- после фильтрации (мкВ → хранить в мкВ)
fiducials(record_id UUID, cycle_idx INT, segment_idx INT,
          r_ms BIGINT, q_on_ms BIGINT NULL, s_off_ms BIGINT NULL,
          p_on_ms BIGINT NULL, p_off_ms BIGINT NULL, t_off_ms BIGINT NULL, j_ms BIGINT NULL,
          baseline_uv REAL, r_amp_uv REAL, ...)
```

Правила: все вставки — батчами (appender); индексация по `(record_id, offset_ms)`; удаление по `record_id`. Запись в DuckDB — через один выделенный сервис (однопоточный писатель), чтобы не было конфликтов блокировок.

> Согласованность: запись в `ecg_records` со статусом `Done` создаётся только после успешной записи в DuckDB. При сбое — откат (удалить частичные данные DuckDB по `record_id`, статус `Failed`).

## 6. Ключевая логика

### 6.1 Валидация CSV (потоковая, до сохранения)

Вход: поток файла. Выход: `ValidationResult { ok, failedCheck (1..12), line?, message }`.

Порядок проверок строго 1→12. Первая сработавшая — финальная.

| № | Проверка | Реализация |
|---|---|---|
| 1 | Расширение `.csv`, размер ≤ 1 ГБ | до чтения содержимого |
| 2 | Корректный UTF-8 | строгий декодер (`UTF8Encoding(false, true)`), BOM допустим только если явно разрешён в ASSUMPTIONS (по умолчанию: BOM отклонять) |
| 3 | Заголовок = ровно {value, timestamp, errors}, регистр нижний, порядок любой, лишних нет | |
| 4 | В каждой строке ровно 3 поля (по запятой, кавычек нет); пустая строка данных — ошибка | |
| 5 | `value`: целое `^-?\d+$`, диапазон −5000…5000 | |
| 6 | `timestamp`: regex `^\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}\.\d{3}$` + реальная дата/время | |
| 7 | `errors` ∈ {`Error`,`NoError`} с учётом регистра | |
| 8 | timestamp строки ≥ предыдущей | |
| 9 | Одинаковый timestamp с разными value/errors | |
| 10 | Медианный интервал между соседними уникальными отсчётами = 4 мс | глобальная; медиана через гистограмму интервалов (мс → счётчик) |
| 11 | Длительность = (last − first) + 4 мс ∈ [10 с, 24 ч] | глобальная |
| 12 | (суммарная длительность разрывов + Error-отсчётов) / длительность ≤ 0.30 | глобальная |

Важно:
- Проверки 1–9 выполняются построчно за один проход; 10–12 — по накопленной статистике после прохода.
- Номер строки ошибки: считать от 1, где строка 1 — заголовок. Для проверок 1, 2 (без позиции), 3, 10–12 строка не указывается (кроме 3 → строка 1).
- Порядок: если на строке 7 нарушена проверка 5, а на строке 5 проверка 7 — какая "первая"? Правило: приоритет по **номеру проверки** внутри одной строки, а по строкам — первая встреченная по порядку чтения. Реализовать: при чтении строки проверять 4→5→6→7→8→9; ошибка возвращается немедленно.
- Идентичные дубликаты — пропускать, не ошибка.
- Шаг > 4 мс между уникальными соседями = разрыв; Error-отсчёт = 4 мс непригодного времени.
- Результат → в `ecg_gaps`. Дубликаты и `Error` в `raw_samples` не попадают.
- Логирование: каждый отказ → `system_logs` (level=Warning, module=`CsvValidation`, code=`CSV_CHECK_<n>`).

### 6.2 Подготовка к анализу

1. Разбить пригодные отсчёты на непрерывные сегменты (по `ecg_gaps`).
2. Сегменты короче `MIN_SEGMENT_SEC = 5` — пропускать анализом (записать как gap `reason=Gap`, пометка «слишком короткий»).
3. Конвертация: мВ = value / 1000.

### 6.3 Фильтрация (приложение Г, этапы 1–2) — на каждом сегменте отдельно

- Высокочастотный срез дрейфа: ФВЧ Баттерворта 0.5 Гц, 2-й порядок, `filtfilt` (нулевая фаза).
- ФНЧ 40 Гц Баттерворт, 4-й порядок, `filtfilt`.
- Режекторный 50 Гц (notch, Q≈30), `filtfilt`.
- Краевые эффекты: отбросить/пометить по 1 с на концах сегмента как «недостоверные края» (не считать там показатели).
- Результат пишется в `filtered_samples`.
- Реализация: `MathNet.Numerics` (MIT) или собственный biquad-каскад. Юнит-тесты: синус 50 Гц ослабляется ≥ 30 дБ; синус 10 Гц ослабляется ≤ 1 дБ; константа 1 мВ (дрейф) → ~0.

### 6.4 Обнаружение QRS (Г.1, этапы 3–5; алгоритм Пана–Томпкинса)

1. Полосовой 5–15 Гц.
2. Дифференцирование (5-точечная производная).
3. Возведение в квадрат.
4. Интегрирование скользящим окном 150 мс.
5. Адаптивные пороги (SPKI/NPKI, двойной порог), refractory 200 мс, search-back при RR > 1.66·RR_avg.
6. Уточнение R: локальный максимум |сигнал| в ±75 мс на **фильтрованном** (не интегральном) сигнале; учесть инвертированные R.
7. Выход: список `r_ms` по сегменту.

Критерий приёмки: на синтетическом сигнале с известным RR ошибка положения R ≤ 8 мс; на тестовых записях чувствительность и положительная предсказательная ценность ≥ 99 %.

### 6.5 Характерные точки (Г.1, этап 6)

Для каждого цикла (если есть предшественник и преемник R):
- **Изолиния** — медиана в окне PR-сегмента (R−80…R−40 мс) либо TP.
- **Q-on / S-off (J)** — по наклону и порогу от R в окне ±120 мс.
- **P-on/off** — окно R−300…Q-on; поиск волны по производной; если амплитуда < `P_MIN_UV` → P = «отсутствует».
- **T-off** — метод касательной/наклона максимального нисхождения в окне J…R+450 мс (или до следующего P).
- Не определено → `NULL`, не выдумывать значение. Циклы с NULL в нужной точке исключаются из соответствующего показателя, учитываются в счётчике «не определено».

### 6.6 Показатели и аномалии (таблица Д.1)

Окно = скользящие 30 с (шаг 5 с, константа), фрагмент = весь непрерывный анализируемый сегмент. Эталонные значения — в `ReferenceRanges.cs`.

| Код | Показатель | Уровень | Вычисление | Аномалия, если |
|---|---|---|---|---|
| HR | ЧСС, уд/мин | окно | 60000 / mean(RR окна, мс) | <60 (брадикардия) или >100 (тахикардия) |
| RR | RR, мс | цикл | R(i+1)−R(i) | <600 или >1000 |
| RR_DEV | Откл. RR от среднего окна, % | цикл | (RRi − RRср)/RRср·100 | \|x\| > 10 |
| PAUSE | Пауза, с | цикл | RR/1000 | ≥ 2.0 |
| R_AMP | Амплитуда R, мВ | цикл + фрагмент | R-пик − изолиния; сравнение со средним окна | вне 0.5…2.5 мВ (фрагмент среднее); на цикле — отклонение от среднего окна (порог отклонения = константа `R_AMP_DEV_PCT = 30`, зафиксировать в ASSUMPTIONS) |
| QRS_SHAPE | Отличие формы, % | цикл | 100·(1 − r), r — Пирсон между комплексом [R−100, R+300] мс и медианным комплексом фрагмента | > 20 |
| QRS_DUR | Длительность QRS, мс | цикл | S-off − Q-on | <60 или >100 (>120 — «выраженное»; хранить как уровень тяжести) |
| PR | Интервал PR, мс | цикл | QRS-on − P-on | <120 или >200 |
| P_WAVE | P: длительность, мс; амплитуда, мВ; доля циклов без P в окне | цикл/окно | | ширина ≥110 мс или амплитуда ≥0.25 мВ; доля без P > `P_ABSENT_FRAC = 0.2` (зафиксировать) |
| QT | QT, мс | цикл | T-off − Q-on | <350 или >450 |
| QTC | QTc, мс (Базетт) | цикл | QT / √(RR/1000) | ≥450 (male) / ≥460 (female) |
| ST | Смещение ST, мВ | цикл | уровень в J+60 мс − изолиния | \|x\| > 0.1 |
| T_WAVE | Амплитуда/полярность T | цикл | | полярность отрицательная или амплитуда > 1.0 мВ |

Правила:
- Цикл не считается, если границы RR пересекают gap/край сегмента.
- Окно с долей пригодных данных < 50 % — показатели окна не вычисляются.
- Если RR_i рядом с gap — не считать паузой.
- Слияние аномалий — по D17.
- Каждая аномалия хранит: код, направление, интервал [start,end] в мс от начала записи, min/max значения, единицы, эталон-строку, число циклов.

### 6.9 Валидация медданных (приложение В)

Реализовать общий набор валидаторов (FluentValidation на backend, зеркало в Angular validators):

- Ошибка → 422 с массивом полей + запись в `system_logs` (module=`MedValidation`).

## 8. Обязательные сквозные тест-сценарии (e2e)

1. Пациент регистрируется → админ ставит согласие → пациент загружает корректный CSV → статус доходит до `Done` → до принятия врачом пациент отчёта НЕ видит.
2. Врач (закреплённый) видит запись → открывает график и отчёт → принимает → пациент теперь видит график и отчёт.
3. Врач создаёт диагноз с привязкой к двум аномалиям → добавляет рекомендацию и назначение → пациент видит их.
4. Незакреплённый врач → 403 при попытке открыть данные чужого пациента; пациент А → 404 на данные пациента Б.
5. Загрузка файла с ошибкой в строке N по проверке 5 → пользователь видит текст причины и номер строки; файл не сохранён; запись в логах есть; админ видит её в `/admin/logs`.
6. Файл с долей непригодного 31 % отклонён (проверка 12); с 29 % — принят, разрывы показаны в отчёте.
7. Админ создаёт врача → получает PDF с временным паролем → врач входит → принуждённая смена пароля → доступ открыт только после неё.
8. Админ блокирует пользователя → его активные токены перестают работать.
9. Удаление мед. данных: без подтверждения — не выполняется; с подтверждением — soft delete, пациент перестаёт видеть.
10. Очистка: запись старше 30 суток → `raw` удалены, отчёт и диагнозы на месте; старше 10 лет → `filtered` удалены.
11. Перезапуск контейнера API посреди анализа → после старта задание возобновляется.
12. Адаптивность: все ключевые экраны на 360 px без горизонтального скролла.
